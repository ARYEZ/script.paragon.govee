v2.1.2
- Supports the newer Broadlink data payload layout. RM4-family devices and
  later "RM Mini 3" units prefix the payload with a two byte length; RM2 and
  RM3-era hardware, including the RM Pro, does not. Only the older layout was
  implemented, so a newer device authenticated perfectly and then refused
  every command with error -5.
- The layout is guessed from the device type code and then corrected by
  experience: a command that fails is retried the other way, and whichever
  works is remembered for the rest of the session. Hardware sold as "RM Mini
  3" spans both generations, so the type code alone cannot be trusted.
- A command that fails both ways reports the original error rather than
  whatever the speculative retry produced, and does not flip the setting.

v2.1.1
- Broadlink device errors are decoded into words and reported as signed
  values, which is how every reference writes them. 0xffff is error -1,
  "Authentication failed".
- An authentication error now carries what to do about it: the device is
  almost certainly locked to the Broadlink app. Turn off "Lock device" in the
  app, and close the app afterwards -- some firmware refuses LAN control while
  the app is holding the device.
- Authentication failures say which step failed. Authentication happens
  lazily on the first command, so a locked device previously looked as though
  learning had failed rather than the handshake.
- New "Test connection" on an emitter's Commands menu. It authenticates and
  reports the result, so a device can be checked without trying to learn a
  code and reading the failure sideways.

v2.1.0
- Broadlink RM support, as the second driver. Discovery, authentication, IR
  learning and sending, all over the LAN with no Broadlink account and no
  cloud.
- Ships a pure-Python AES-128-CBC, because the Broadlink protocol encrypts
  every packet and Kodi 17.6's Python 2.7 has no crypto library. Verified
  against the FIPS-197 AES-128 vector and the NIST SP 800-38A CBC vector.
- An RM appears in Manage devices with a Commands entry rather than
  Identify: it has no light to flash. From there you can learn a code, send
  one, or delete one.
- Learning puts the device into learning mode and polls for up to 30 seconds
  while you press the button on your remote; it can be cancelled.
- Learned codes are stored in broadlink_codes.json in the add-on profile,
  alongside scenes, devices and colours.
- Scene actions can now fire a learned code, so one scene dims the lights and
  switches the amp on.
- The device type code is persisted with the device. Broadlink puts it in
  every packet header, so guessing it after a restart would build packets the
  device silently ignores.

v2.0.0
- Restructured around a driver interface, so vendors other than Govee can be
  added without touching the device registry, the scene engine or the menus.
  Govee becomes the first driver. Nothing about your lights, scenes, colours
  or names changes, and the add-on id is unchanged so your saved data carries
  over untouched.
- New Hub layer routes every device operation to the driver that owns it.
  Devices record which driver found them; a devices.json written before this
  records none and is read as Govee, which is what it is.
- Devices now report capabilities (power, brightness, colour, colour
  temperature, state, commands) rather than the scene engine assuming every
  device is a colour bulb. Only what a device claims is ever asked of it.
- Scenes gain actions: {'device': id, 'command': name}. That is how a scene
  reaches a device with no state to set -- an IR blaster has no colour, it
  has "AVR Power" -- so one scene can dim the lights and switch the amp on.
- One driver failing a search no longer hides the others, and state reads are
  grouped per driver so Govee keeps its single-socket bulk sweep.
- The add-on is now called Paragon Home. The id stays script.paragon.govee so
  no reinstall is needed and no saved data moves.

v1.7.1
- A cycle step now sends only the colour. Power and brightness are already
  where the previous step left them, so re-sending them was two thirds of the
  traffic for no visible effect -- with 25 lights and retries, roughly 150
  datagrams a step rather than 50.
- Scene application paces its sends a few milliseconds apart. A burst of
  datagrams to every light at once is the shape of traffic consumer access
  points drop, which was already measured to cost status replies on this
  hardware. Over 25 lights the whole pause is about a tenth of a second, and
  a dropped colour command during a cycle leaves a bulb visibly stuck until
  the next tick.

v1.7.0
- Mix scenes can cycle. In the scene editor, "Cycle colours" sets how often
  every light moves along to the next colour in the mix: 15 seconds up to 15
  minutes, or off.
- Stepping rotates the arrangement rather than re-dealing it. That keeps the
  even spread exactly -- a 9/8/8 split becomes 8/8/9, never 12/7/6 -- and
  guarantees every light actually changes colour, which a fresh random deal
  would not.
- The background service does the stepping, so cycling continues while you
  browse Kodi, and carries on after a Kodi restart.
- Applying any other scene stops a running cycle, so dimming for a film is
  not overwritten a minute later by a party still stepping in the background.
  The main menu grows a "Stop cycling" row while one is running.
- Setting a cycle warns first if the lights are driven over the Govee cloud
  and the interval would exceed the daily call quota. 25 cloud lights on a
  one-minute cycle is about 36,000 calls a day against a limit near 10,000.
  Cycling is really a LAN feature.
- Lights added after a cycle starts are dealt in on the next step rather than
  being left on whatever they were showing.

v1.6.0
- Scenes can now hold a mix of colours. In the scene editor choose
  Appearance -> "Mix of colours (spread over the lights)..." and tick as many
  saved colours as you like; applying the scene deals them across the lights.
- The spread is even, not merely random: each colour is used floor(n/k) or
  ceil(n/k) times, so 25 lights and 3 colours is 9/8/8 rather than whatever
  chance produces. Which light gets which is shuffled, so the same scene
  arranges differently every time it is applied.
- Which colour gets the spare light is also randomised. Repeating and
  truncating the colour list alone would hand it to the first colour every
  single time, which shows up as a bias over repeated applications.
- Mix colours are copied into the scene rather than referenced by name, so
  editing or deleting a palette colour later cannot silently change or empty
  a scene that was already built and tested.
- A per-light entry from a capture still wins over the mix, so the two
  features compose rather than fighting.

v1.5.0
- The colour list is now editable. "Manage colours..." at the bottom of any
  colour menu lets you add a colour by hex code and name it, rename it,
  change its hex, move it up or down the list, delete it, or reset the whole
  list to the built-in set.
- Colours are stored in palette.json in the add-on profile, alongside
  scenes.json and devices.json, so they survive upgrades and can be
  hand-edited or copied to another Kodi box.
- Colour rows now show their hex, e.g. "Paragon Purple  #963CDC".
- The saved colours are what the scene editor offers too, so a colour added
  once is available everywhere.
- RunScript(action=color) accepts a saved colour name as well as a hex code,
  so a colour on the speed dial can be bound to a remote button by name.
- The built-in colours were previously a hardcoded list in the code; they are
  now just the seed for the editable one.

v1.4.0
- A light that does not answer a search is no longer dropped from the device
  list. It used to be erased along with its name and its enabled flag, so one
  sleeping WiFi bulb during a refresh could undo a trip around the house. Its
  entry is now kept as it was, and the refresh summary says how many lights
  did not answer.
- New "Forget this light" in a light's Manage devices menu, for one that has
  genuinely been removed rather than being temporarily quiet.
- Names are unaffected by switching transports: a name that is not the
  model-plus-id placeholder is carried across every refresh, so names picked
  up from the Govee cloud stay after switching to LAN only. Now covered by a
  test that walks that exact round trip.

v1.3.1
- Identify now flashes 10 times rather than 3 -- about eight seconds, long
  enough to walk into the next room and still catch it.
- Identify shows a progress dialog and can be cancelled, so it stops the
  moment the light is spotted instead of having to be waited out.
- Identify puts the light back to the state it was in. It used to leave the
  bulb switched on regardless, so identifying a light that was off silently
  turned it on for good.

v1.3.0
- New "Name lights one by one..." at the top of Manage devices. Each light
  comes on bright magenta in turn and stays lit while the keyboard is up, so
  the light you are naming is on the wall in front of you as you type. It is
  put back to its previous state before the walk moves on, and cancelling the
  keyboard stops the walk keeping every name entered so far.
- When some lights are already named, the walk offers to cover only the ones
  still on their placeholder name.
- Manage devices rows are now (label, handler) pairs like the other menus.
- Extracted scenes.apply_settings(), now shared by scene application, the
  status round-trip's restore step and the naming walkthrough, so the
  brightness-before-colour ordering lives in one place instead of three.

v1.2.1
- Confirmed the Govee colour format from real codes out of the app
  (FF3C447F, FF7F3C3C): it is AARRGGBB with the alpha always FF. Read the
  other way round those would mean alphas of 7F and 3C -- bulbs at 50% and 23%
  transparency -- so AARRGGBB is the only sensible reading. No behaviour
  change; the inference already produced this. Both codes are now test cases,
  along with the case where a Govee colour ends in FF and the ambiguous
  alpha-first default is what keeps it correct.

v1.2.0
- Colour entry now accepts the 8-digit hex codes the Govee app uses, not just
  6-digit ones. Pasting a Govee code used to be rejected outright.
- Which end the alpha byte sits on is inferred rather than assumed: Android
  writes AARRGGBB, CSS writes RRGGBBAA, and Govee documents neither. An alpha
  in a colour picker is almost always FF, so whichever end is FF is taken as
  the alpha; when both ends are FF or neither is, the readings are genuinely
  indistinguishable and alpha-first wins.
- The confirmation says how a code was read ("read as AARRGGBB"), because
  dropping the alpha off the wrong end silently produces a different colour
  and that should be visible, not a surprise on the wall.
- RunScript(action=color) shares the same parser, so keymaps and favourites
  accept Govee codes too.

v1.1.5
- Documentation only. The status round-trip has now been run on real hardware:
  an H6008 set to RGB 255,0,255 at 40% over the LAN reported back exactly that.
  So devStatus on this model is honest -- it reports the last state set over
  the LAN, and a cloud-applied Govee app scene layered on top is invisible to
  it. The README said this was unknown; it now says what was measured, and
  gives the steps for building a scene in Kodi rather than capturing one.

v1.1.4
- New "Check status reporting..." on a single light's menu, also reachable as
  RunScript(script.paragon.govee,action=verifystatus). It sets the bulb to a
  known colour, reads the status back, reports whether the two agree, and puts
  the bulb back. Capture, Toggle and Show status all trust devStatus, so
  whether a model keeps it up to date decides whether those features can work
  at all -- and no single capture can tell a stale reading apart from a light
  that something else had set.
- The probe uses a second colour when the bulb already shows the first, since
  probing with the colour already displayed could not distinguish a stale
  reading from a correct one.

v1.1.3
- Fixed a coloured bulb being captured as white. Govee reports both a colour
  and a colour temperature, and they can disagree; taking the temperature
  first meant a bulb showing pink alongside a stale 3800K reading was captured
  as 3800K white. A tinted colour now wins, and a grey or zero colour -- which
  carries no colour information -- still defers to the temperature.
- The capture dialog now says what capture cannot see: the Govee LAN protocol
  has no scene concept, so a bulb driven into a scene by the Govee app keeps
  reporting whatever was last set locally. Capture records what the bulb
  reports, which for an app-set scene is not what you are looking at.

v1.1.2
- Fixed capture appearing to hang. Any bulb the bulk status sweep missed was
  re-read individually, and each of those re-binds UDP 4002 and waits out its
  own timeout -- with 25 bulbs that is well over half a minute of the progress
  bar sitting there. Only non-LAN devices fall back individually now; the bulk
  sweep does its own retry round.
- Bulk status now staggers its requests by a few milliseconds and retries the
  bulbs that stayed silent. A burst of 25 datagrams is exactly what a consumer
  access point drops, and WiFi bulbs in power-save routinely miss the first
  packet, which left them missing from a capture.
- Capture now detects the brightness scale. Govee documents brightness as
  0-100 but some models report the raw 0-254 register; that was being clamped
  to 100, which flattened every bulb above about 39% to full. The scale is
  detected across the whole capture, because a single reading of 51 could be
  51% or 20% and cannot be told apart on its own.
- Capture writes every bulb's raw reading to kodi.log, and the confirmation
  dialog now summarises what it read -- how many colour, white and off, and
  the brightness spread -- so a wrong-looking capture is visible immediately.

v1.1.1
- "Capture lights as a scene..." is now on the main menu as well as inside
  Scenes, where it was easy to miss.
- The main menu title shows the running version, so a `git pull` can be
  confirmed at a glance.
- Main menu rows are now (label, handler) pairs like the rest of the menus,
  which removes the last place where inserting a row could rewire the ones
  below it.

v1.1.0
- New "Capture lights as a new scene..." in the Scenes menu. It snapshots what
  every light is doing right now and saves it as a scene. This is the way to
  get a Govee Tap-to-Run into Kodi: run it in the Govee app, then capture the
  result. The saved copy replays over the LAN, so it needs no Govee account
  credentials and no cloud call.
- Scenes can now carry a different setting per light, not just one uniform
  setting for all of them. Scenes without per-light entries are unchanged, and
  a light with no entry falls back to the scene's own values.
- Added bulk status reads: the whole set of lights is queried in one pass
  instead of one bind and one timeout each. Capturing 25 bulbs now costs about
  one timeout rather than the better part of a minute.
- Cloud and LAN state readings are now normalised onto the same keys. The
  cloud reported powerState where the LAN reported onOff, which pushed the
  difference onto every caller.

v1.0.2
- LAN search now sends the scan from every local interface rather than only
  whichever one the routing table prefers, which is what broke discovery on
  multi-homed boxes (VPN, Hyper-V or docker bridge, wired plus wireless).
- Added a plain broadcast fallback alongside the multicast scan, for networks
  that drop or fail to flood 239.255.255.250.
- New "Diagnose LAN search..." tool in the control panel, also reachable as
  RunScript(script.paragon.govee,action=diagnose). It distinguishes the reply
  port being held by another program, the scan failing to send, replies that
  are not Govee, and total silence, and writes the full detail to kodi.log.
- A failed bind on UDP 4002 now names the likely culprit instead of reporting
  a generic error.
- Fixed the diagnostic device count including one entry per probe path, which
  would have reported several times the real number of lights.

v1.0.1
- Fixed the background service crashing on startup with "TypeError: an
  integer is required". Kodi parses xbmc.Player constructor arguments in the
  base type, before a subclass __init__ runs, so the player subclass must
  take no arguments; the service now attaches itself after construction.
- Player callbacks are inert before the service attaches and after it
  detaches, so a callback arriving during startup or shutdown is a no-op.
- Test stubs now reproduce Kodi's constructor-argument parsing for both
  xbmc.Player and xbmc.Monitor, so this class of failure is caught off-device.

v1.0.0
- First release.
- Govee LAN transport: multicast discovery, power, brightness, colour, colour
  temperature and status, with no API key and no rate limit.
- Govee Cloud transport as a fallback for lights without LAN Control.
- Automatic per-device transport selection; LAN preferred when available.
- Devices found on both transports are merged into one entry.
- Control panel: per-light and all-lights power, brightness, colour and colour
  temperature, plus device rename, enable/disable and identify.
- User-editable scenes, seeded with Movie Night, Paused, Lights Up,
  Warm Evening, Paragon Purple and All Off.
- Playback lighting service: applies scenes on play, pause and stop, with
  content-type, fullscreen and delay filters. Only restores on stop if it was
  the thing that dimmed the lights.
- RunScript() actions for keymaps and favourites, with optional per-light
  targeting by name or device id.
