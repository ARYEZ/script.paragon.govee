v2.13.0
- A rerack can now follow Paragon TV. Paragon TV has a Rerack of its own -- a
  nine-phase preset macro system with one preset per day -- and a rerack here
  can hang off one of those phases instead of keeping its own clock, so the
  lights come up when the channel does and the room goes dark when the box
  shuts down.
- It runs whenever that phase falls for whichever preset today is. The same
  rerack runs at 07:00 on an Alpha day and 08:00 on a Sigma day, because
  Paragon TV's weekly table decides, not a fixed time here.
- Following a phase replaces the rerack's own time and days rather than adding
  to them. Two schedules on one rerack would be two answers to one question.
- Nothing runs on a day Paragon TV has no preset for, on a phase a preset does
  not carry -- the satellite presets have no maintenance phase -- or while
  Paragon TV's own preset system is switched off. A phase whose time moves
  re-arms the rerack, because the record holds the time as well as the date.
- New "What Paragon TV says about today" lists today's preset and every phase
  time it holds, so a phase can be checked before it is relied on.
- Paragon TV's settings are only ever read, never written, and are read the
  way Paragon TV reads them: the day settings hold an index rather than a
  name, and reading one as a name would find nothing without saying so.
  Paragon TV needs no change and does not need to know this exists.

v2.12.0
- A rerack can now run itself: "Runs:" in the rerack editor gives it a time
  and the days it applies to, so "Ignition" can run on Saturdays at 6pm.
- The time is read forgivingly. 18:00, 6pm, 6:30 PM and 1800 all mean the same
  thing, which matters when it is being typed on a remote control.
- Both a time and at least one day are needed. Either alone is a schedule that
  can never come round, so it counts as unscheduled until it has both.
- A scheduled rerack runs once per day, recorded on disk so restarting Kodi
  does not re-run it. A few minutes late still counts, because Kodi is not
  always awake at the exact minute; an hour late does not, because a rerack
  that lifts the lights at six should not do it at seven.
- It is marked as run before it runs, not after: a rerack that failed half way
  would otherwise be due again on the next tick and every tick after that.
- Moving a schedule later in the same day lets it run again. The record holds
  the time as well as the date, on purpose.
- Firing happens in the background service, which already stops cleanly on
  shutdown -- so closing Kodi during a rerack full of pauses does not wait for
  it to finish.
- Deleting a rerack forgets when it last ran, so a new one given the same name
  does not inherit a day it never had.

v2.11.0
- The commands a scene sends are now editable. They have worked in the engine
  since v1.1 but there was no way to add one short of editing scenes.json by
  hand: "Commands to send" in the scene editor picks a device that has learned
  codes and one of its codes, so a single "Movie Night" can dim the lights and
  switch the amplifier on.
- Tuya plugs: "After a power cut" sets what the relay does when mains power
  returns -- stay off, come back on, or remember how it was. It is a setting
  on the plug, so it covers every outlet on it and holds whether or not Kodi
  is running. The value is read from the plug rather than remembered here, and
  a plug without one says so rather than showing a made-up setting.
- "Switch on" and "Switch off" now appear for any device that switches. They
  were written when Tuya was the only plug driver and were gated on needing a
  local key, which quietly denied a Kasa plug the two rows it most wants.
- The scene editor is built from rows with handlers rather than a list read
  back by index. It had grown a row four times, and each time the numbering
  under it had to be re-counted by hand.

v2.10.1
- Fixed a rerack whose steps included a scene switching every plug in the
  house. The scene was doing it, not the plug step beside it.
- A scene that names no targets now applies to what it can actually describe,
  rather than to every enabled device. Scenes predate plugs: naming no targets
  meant "all the lights" because lights were all there was, and when plugs
  were added to the device list "all" silently widened to include them. A
  colour scene then switched every plug as a side effect of the power setting
  that came with the colour.
- A scene that only says "off" still reaches everything, because off is
  something a plug can be. A scene that names its targets is honoured exactly,
  which is how a plug joins a colour scene deliberately.
- The scene editor now says which "all" it means: "all colour devices" or
  "all devices". It said "all lights", which stopped being true.

v2.10.0
- Reracks: ten ordered steps run as one, under "Reracks..." on the first
  screen. Named after the Paragon TV preset macro system and shaped like it --
  a fixed set of numbered slots rather than a list you grow, so a rerack has
  the same shape every time you open it and slot 4 is always slot 4.
- A step is three choices in the order you would say them: what kind of thing,
  which one, and what to do to it. Scene, or a device of any driver with On,
  Off, Toggle or one of its learned infrared commands.
- Each step can hold a pause afterwards. A television told to switch on and
  change channel in the same breath will miss the second command, and this is
  the only way to say so.
- A failing step does not stop the ones after it. Every failure is collected
  and reported together at the end, because a rerack is a list of separate
  intentions and an unplugged plug is no reason to leave the room dark.
- Steps refer to devices by id, so renaming a device does not break a rerack
  that used it. A rerack written by hand can name a device instead.
- A long rerack runs behind a progress dialog that can be cancelled part way.
- Every rerack is a RunScript() target:
  RunScript(script.paragon.govee,action=rerack,name=Wind Down)

v2.9.0
- When some Kasa plugs accept the account and others refuse it, the add-on now
  says which of two quite different things is happening. A plug never bound to
  a TP-Link account answers with no credentials at all, so it works whether
  the details in Settings are right or wrong -- which means a mix of working
  and failing plugs can have a single cause, and it looks like nonsense until
  you know which kind each plug is.
- "Test connection" now reports whether your account was what got in, or
  whether that plug needed no account and so proves nothing.
- TP-Link's own published setup credentials are tried as well, which a device
  in setup state answers to.
- A failed handshake logs its seeds and the hash the device returned. Those
  contain no password and cannot be used to derive one, but they are enough to
  work out offline what the device actually wants.
- New tools/kasa_klap_probe.py asks a plug directly which credentials and
  which hash scheme it wants, trying more variants than the add-on
  implements. The password is prompted for and never printed, stored or sent
  anywhere but the plug.

v2.8.2
- Fixed "'ascii' codec can't decode byte 0xcc in position 0" when switching a
  later Kasa plug. A Python 2 trap, and the ordinary case rather than an edge
  one: a device address read back from devices.json is unicode, because that
  is what json.load produces on Python 2. That made the request URL unicode,
  which made the Host header unicode, and Python 2's httplib joins the headers
  into one string before appending the body -- so the binary handshake payload
  was implicitly decoded as ascii and failed on its first random byte.
- Every URL and header value in an HTTP request is now the interpreter's own
  str type. The same latent fault was in the Govee cloud client and is fixed
  there too, before it had a chance to surface.
- Two more implicit decodes removed from the KLAP path, both the same shape.

v2.8.1
- A device whose state could not be read was always blamed on Govee. The
  dialog named UDP port 4002 -- the port Govee's status reply uses and which a
  Kasa plug has never heard of -- so a Kasa or Tuya failure was reported as a
  Govee one and the real reason was thrown away.
- It now asks the driver again through its own connection test, which does
  report a reason, and shows that instead. Govee keeps the port explanation,
  because Govee is the one driver with no connection test and the one whose
  status read contends for a well-known port.
- A plug was being offered "Identify (flash this light)", which it cannot do,
  and no connection test, which it can. Identify is now offered only to
  something that can show a colour, and a connection test to any device whose
  driver has one.
- Fixed a KLAP error message printing a literal backslash-n instead of a line
  break.
- The KLAP handshake now also tries blank credentials, which is what a device
  never bound to a TP-Link account uses. Nothing in the announcement
  distinguishes one, and the device's own handshake hash says which is right.

v2.8.0
- Later Kasa hardware is now supported. An HS103 hardware v2 and an HS103
  hardware v5 are the same model number in the same box, and speak entirely
  different protocols: the v2 answers an open protocol on port 9999, and the
  v5 does not answer port 9999 at all. That is why a search found one plug and
  not the others, and no amount of sweeping was ever going to fix it.
- Later hardware speaks KLAP over HTTP, and will not answer until both ends
  have proved they know the password of the TP-Link account the plug is
  registered to. Enter that account under Settings -> Kasa. It is used on your
  own network only -- nothing is sent to TP-Link -- but it is stored in Kodi's
  settings in plain text, which is worth knowing.
- A search now sends both generations' queries together, since which one a
  plug is cannot be known before asking. Later hardware announces on a
  different UDP port and says which protocol it speaks, so it is listed and
  named before an account is entered, and says what it needs rather than
  looking broken.
- Two credential hash schemes exist and the device does not say which it
  wants. Both are derived and compared against the hash the device returns in
  its handshake, which is a definite answer rather than a guess.
- Nothing changes for older hardware: no account, no key, exactly as before.
  A device cached before this release is treated as the older protocol.

v2.7.2
- The Kasa sweep was covering the wrong subnet, so a search still found only
  the plugs broadcast could reach. It worked out which subnet to sweep from
  this machine's own addresses, which on a box with a VPN, a container bridge
  or an unhelpful hostname is a confident wrong answer -- and sweeping the
  wrong /24 looks exactly like sweeping the right one and finding nothing.
- The range now comes from every device already known to be on the network:
  one the search has just found, and anything already in the device list,
  whatever its brand. A Govee bulb's address states which subnet the house is
  on better than this machine's own can.
- The Kasa diagnostic now reports what the search did rather than only what it
  found: how many each pass turned up, which subnet was swept and how many
  hosts that covered, and which addresses it went out from. Reporting only the
  devices could not tell "the sweep ran and they are not there" apart from
  "the sweep never ran", which need opposite responses.

v2.7.1
- Fixed a Kasa search finding only some of the plugs. Two causes, one mine.
- Mine: the search sent from a socket it closed immediately afterwards. A Kasa
  device answers to the port the request came from, so every reply to those
  sends was discarded, and only the devices that happened to answer the one
  send from the socket that stayed open were ever found.
- Not mine: broadcast traffic. Mesh access points and guest networks routinely
  drop or fail to flood it, which reaches some devices and not others. After
  broadcasting, the search now addresses every host on the subnet directly,
  which does not depend on broadcast working at all. The Kasa app broadcasts
  too, so it can show fewer devices than this does for the same reason.
- When the sweep turns up devices the broadcast missed, the search says so.
  Silently working around a network fault would hide it.
- The broadcast now goes out three times rather than once. UDP has no
  retransmission, and several devices answering at once is exactly when one
  goes missing.
- A search stops as soon as everything has gone quiet instead of sitting out
  its whole window, so finding everything is usually about a second.

v2.5.0
- Multi-outlet plugs get an "All outlets" entry that switches the whole box,
  for a bedtime scene or a leaving-the-house button.
- There is no master relay to switch: nothing in a Tuya socket's instruction
  set turns the box off as a unit, and the phone app's "all off" is every
  outlet set in one command. This does the same, so the outlets go together
  rather than in sequence and it costs one round trip instead of one per
  outlet.
- The whole-plug entry reads as on when anything is drawing power, not only
  when everything is. Requiring all of them would report a strip with one
  outlet live as off, and the button that followed would turn it further on.
- A bulk action such as "everything off" now uses the whole-plug entry and
  skips its outlets, which is the same result in a quarter of the packets. A
  scene is deliberately left alone, since a scene can tell outlets different
  things and folding them would silently drop one.
- Which outlets the entry covers is recorded when the plug is found, so it
  keeps working after a restart without another round trip. One saved before
  this release falls back to every socket datapoint Tuya defines, which a
  plug ignores where it has none.

v2.4.0
- Tuya protocol 3.4 is now driven, which is what the GHome WP9 speaks. 3.4 is
  a different protocol wearing the same version number: it negotiates a
  session key on every connection, signs each packet with HMAC-SHA256 rather
  than a CRC32, renumbers both verbs, and moves the version header inside the
  encryption instead of in front of it.
- A wrong key on 3.4 is caught at the handshake, where the HMAC gives a
  definite answer, rather than several steps later as a reply that will not
  decrypt.
- Not every 3.4 reply carries a return code and nothing in the header says
  which do. Every payload is AES-ECB ciphertext, so the reading that leaves a
  whole number of blocks is the right one -- a check against the format
  rather than a guess between two options.
- 3.5 is still not driven: it encrypts with AES-GCM, which is a different
  cipher rather than a bigger version number. A 3.5 plug is discovered,
  listed, and says which version it speaks.

v2.3.0
- Tuya smart plugs can now be switched, not just found. Control is LAN only:
  the cloud account is used once to fetch a local key and never again.
- Multi-outlet plugs are listed one device per outlet. A three-outlet strip is
  three independent switches in one box, and listing it as a single device
  would mean a scene could only turn all of it on or all of it off.
- Which outlets exist is read from the plug rather than guessed from a table
  of product ids, so a plug nobody has heard of splits correctly too. Mains
  outlets and USB banks are told apart from countdown timers, relay memory and
  the child lock.
- A single-outlet plug stays a single device rather than being called
  "Outlet 1", and an entry cached before this release still switches.
- Outlets of one plug share a single status round trip, which also keeps their
  readings consistent with each other.
- One key covers every outlet of a plug: it belongs to the hardware, so it is
  not typed in three times.
- New "Test connection" on a keyed device, and "Switch on"/"Switch off" in its
  own menu. Sixteen characters typed on a remote is an easy thing to get one
  keystroke wrong, and this says so immediately instead of leaving a plug that
  silently will not switch.
- A wrong key is now named as the likely cause. The device refuses the request
  and its reason comes back encrypted under the key we do not have, so the
  honest reading of an unreadable error on this protocol is a key mismatch --
  better than showing the user a character decoding failure.
- Protocol 3.1 through 3.3 are driven. 3.4 and 3.5 negotiate a session key
  first; a plug on one of those is still discovered and says which version it
  speaks rather than failing obscurely.
- Scenes ask the driver what a device can do instead of what a Govee bulb
  lists. A plug in a scene is switched and sent nothing else, so one scene can
  drive bulbs and plugs together.
- The device menu is built from what the device actually is, rather than a
  list read back by position. Every new device type used to shift the
  numbering under the rows below it.

v2.2.1
- New Tuya search diagnostic, under "Diagnose device search..." on the main
  menu, which now offers one per driver since each fails its own way.
- It reports whether each Tuya port could be opened, counts every datagram
  that arrived including ones it could not parse, and dumps the first few as
  raw bytes to kodi.log. Silence, a port held by another program, and traffic

v2.2.0
- Finds Tuya smart plugs, as the third driver. That covers GHome, Gosund,
  Smart Life and most no-name plugs, which are all the same platform.
- Discovery is passive: Tuya devices announce themselves by UDP broadcast
  rather than answering a probe, so the search listens on ports 6666 and 6667
  for at least one announce interval rather than doing a quick sweep.
- Both broadcast forms are handled -- clear 3.1 and AES-encrypted 3.3+ -- and
  both payload offsets are tried, since neither is announced and guessing
  wrong would mean silently finding nothing.
- Added AES-128-ECB, which Tuya uses where Broadlink uses CBC. Verified
  against the NIST SP 800-38A ECB vector.
- Switching a plug needs its local key, which exists only in Tuya's cloud and
  is never offered by the device. A plug without one is still discovered,
  listed and nameable, and says what it needs rather than looking broken.
  "Set local key" in a plug's Manage devices menu takes it.
- Device ids keep their original case alongside the upper-cased matching
  form. Tuya ids are lower case and go on the wire verbatim, so upper-casing
  one would produce an id the device disowns.

v2.1.2
- Supports the newer Broadlink data payload layout. RM4-family devices and
  later "RM Mini 3" units prefix the payload with a two byte length; RM2 and
  RM3-era hardware, including the RM Pro, does not. Only the older layout was
  implemented, so a newer device authenticated perfectly and then refused
  every command with error -5.
- The layout is guessed from the device type code and then corrected by
  experience: a command that fails is retried the other way, and whichever
  works is remembered for the rest of the session. Hardware sold as "RM Mini
  3" spans both generations, so the type code alone cannot be trusted.
- A command that fails both ways reports the original error rather than
  whatever the speculative retry produced, and does not flip the setting.

v2.1.1
- Broadlink device errors are decoded into words and reported as signed
  values, which is how every reference writes them. 0xffff is error -1,
  "Authentication failed".
- An authentication error now carries what to do about it: the device is
  almost certainly locked to the Broadlink app. Turn off "Lock device" in the
  app, and close the app afterwards -- some firmware refuses LAN control while
  the app is holding the device.
- Authentication failures say which step failed. Authentication happens
  lazily on the first command, so a locked device previously looked as though
  learning had failed rather than the handshake.
- New "Test connection" on an emitter's Commands menu. It authenticates and
  reports the result, so a device can be checked without trying to learn a
  code and reading the failure sideways.

v2.1.0
- Broadlink RM support, as the second driver. Discovery, authentication, IR
  learning and sending, all over the LAN with no Broadlink account and no
  cloud.
- Ships a pure-Python AES-128-CBC, because the Broadlink protocol encrypts
  every packet and Kodi 17.6's Python 2.7 has no crypto library. Verified
  against the FIPS-197 AES-128 vector and the NIST SP 800-38A CBC vector.
- An RM appears in Manage devices with a Commands entry rather than
  Identify: it has no light to flash. From there you can learn a code, send
  one, or delete one.
- Learning puts the device into learning mode and polls for up to 30 seconds
  while you press the button on your remote; it can be cancelled.
- Learned codes are stored in broadlink_codes.json in the add-on profile,
  alongside scenes, devices and colours.
- Scene actions can now fire a learned code, so one scene dims the lights and
  switches the amp on.
- The device type code is persisted with the device. Broadlink puts it in
  every packet header, so guessing it after a restart would build packets the
  device silently ignores.

v2.0.0
- Restructured around a driver interface, so vendors other than Govee can be
  added without touching the device registry, the scene engine or the menus.
  Govee becomes the first driver. Nothing about your lights, scenes, colours
  or names changes, and the add-on id is unchanged so your saved data carries
  over untouched.
- New Hub layer routes every device operation to the driver that owns it.
  Devices record which driver found them; a devices.json written before this
  records none and is read as Govee, which is what it is.
- Devices now report capabilities (power, brightness, colour, colour
  temperature, state, commands) rather than the scene engine assuming every
  device is a colour bulb. Only what a device claims is ever asked of it.
- Scenes gain actions: {'device': id, 'command': name}. That is how a scene
  reaches a device with no state to set -- an IR blaster has no colour, it
  has "AVR Power" -- so one scene can dim the lights and switch the amp on.
- One driver failing a search no longer hides the others, and state reads are
  grouped per driver so Govee keeps its single-socket bulk sweep.
- The add-on is now called Paragon Home. The id stays script.paragon.govee so
  no reinstall is needed and no saved data moves.

v1.7.1
- A cycle step now sends only the colour. Power and brightness are already
  where the previous step left them, so re-sending them was two thirds of the
  traffic for no visible effect -- with 25 lights and retries, roughly 150
  datagrams a step rather than 50.
- Scene application paces its sends a few milliseconds apart. A burst of
  datagrams to every light at once is the shape of traffic consumer access
  points drop, which was already measured to cost status replies on this
  hardware. Over 25 lights the whole pause is about a tenth of a second, and
  a dropped colour command during a cycle leaves a bulb visibly stuck until
  the next tick.

v1.7.0
- Mix scenes can cycle. In the scene editor, "Cycle colours" sets how often
  every light moves along to the next colour in the mix: 15 seconds up to 15
  minutes, or off.
- Stepping rotates the arrangement rather than re-dealing it. That keeps the
  even spread exactly -- a 9/8/8 split becomes 8/8/9, never 12/7/6 -- and
  guarantees every light actually changes colour, which a fresh random deal
  would not.
- The background service does the stepping, so cycling continues while you
  browse Kodi, and carries on after a Kodi restart.
- Applying any other scene stops a running cycle, so dimming for a film is
  not overwritten a minute later by a party still stepping in the background.
  The main menu grows a "Stop cycling" row while one is running.
- Setting a cycle warns first if the lights are driven over the Govee cloud
  and the interval would exceed the daily call quota. 25 cloud lights on a
  one-minute cycle is about 36,000 calls a day against a limit near 10,000.
  Cycling is really a LAN feature.
- Lights added after a cycle starts are dealt in on the next step rather than
  being left on whatever they were showing.

v1.6.0
- Scenes can now hold a mix of colours. In the scene editor choose
  Appearance -> "Mix of colours (spread over the lights)..." and tick as many
  saved colours as you like; applying the scene deals them across the lights.
- The spread is even, not merely random: each colour is used floor(n/k) or
  ceil(n/k) times, so 25 lights and 3 colours is 9/8/8 rather than whatever
  chance produces. Which light gets which is shuffled, so the same scene
  arranges differently every time it is applied.
- Which colour gets the spare light is also randomised. Repeating and
  truncating the colour list alone would hand it to the first colour every
  single time, which shows up as a bias over repeated applications.
- Mix colours are copied into the scene rather than referenced by name, so
  editing or deleting a palette colour later cannot silently change or empty
  a scene that was already built and tested.
- A per-light entry from a capture still wins over the mix, so the two
  features compose rather than fighting.

  now just the seed for the editable one.

v1.2.1
- Confirmed the Govee colour format from real codes out of the app
  (FF3C447F, FF7F3C3C): it is AARRGGBB with the alpha always FF. Read the
  other way round those would mean alphas of 7F and 3C -- bulbs at 50% and 23%
  transparency -- so AARRGGBB is the only sensible reading. No behaviour
  change; the inference already produced this. Both codes are now test cases,
  along with the case where a Govee colour ends in FF and the ambiguous
  alpha-first default is what keeps it correct.

v1.2.0
- Colour entry now accepts the 8-digit hex codes the Govee app uses, not just
  6-digit ones. Pasting a Govee code used to be rejected outright.
- Which end the alpha byte sits on is inferred rather than assumed: Android
  writes AARRGGBB, CSS writes RRGGBBAA, and Govee documents neither. An alpha
  in a colour picker is almost always FF, so whichever end is FF is taken as
  the alpha; when both ends are FF or neither is, the readings are genuinely
  indistinguishable and alpha-first wins.
- The confirmation says how a code was read ("read as AARRGGBB"), because
  dropping the alpha off the wrong end silently produces a different colour
  and that should be visible, not a surprise on the wall.
- RunScript(action=color) shares the same parser, so keymaps and favourites
  accept Govee codes too.

v1.1.5
- Documentation only. The status round-trip has now been run on real hardware:
  an H6008 set to RGB 255,0,255 at 40% over the LAN reported back exactly that.
  So devStatus on this model is honest -- it reports the last state set over
  the LAN, and a cloud-applied Govee app scene layered on top is invisible to
  it. The README said this was unknown; it now says what was measured, and
  gives the steps for building a scene in Kodi rather than capturing one.

v1.1.4
- New "Check status reporting..." on a single light's menu, also reachable as
  RunScript(script.paragon.govee,action=verifystatus). It sets the bulb to a
  known colour, reads the status back, reports whether the two agree, and puts
  the bulb back. Capture, Toggle and Show status all trust devStatus, so
  whether a model keeps it up to date decides whether those features can work
  at all -- and no single capture can tell a stale reading apart from a light
  that something else had set.
- The probe uses a second colour when the bulb already shows the first, since
  probing with the colour already displayed could not distinguish a stale
  reading from a correct one.

v1.1.3
- Fixed a coloured bulb being captured as white. Govee reports both a colour
  and a colour temperature, and they can disagree; taking the temperature
  first meant a bulb showing pink alongside a stale 3800K reading was captured
  as 3800K white. A tinted colour now wins, and a grey or zero colour -- which
  carries no colour information -- still defers to the temperature.
- The capture dialog now says what capture cannot see: the Govee LAN protocol
  has no scene concept, so a bulb driven into a scene by the Govee app keeps
  reporting whatever was last set locally. Capture records what the bulb
  reports, which for an app-set scene is not what you are looking at.

v1.1.2
- Fixed capture appearing to hang. Any bulb the bulk status sweep missed was
  re-read individually, and each of those re-binds UDP 4002 and waits out its
  own timeout -- with 25 bulbs that is well over half a minute of the progress
  bar sitting there. Only non-LAN devices fall back individually now; the bulk
  sweep does its own retry round.
- Bulk status now staggers its requests by a few milliseconds and retries the
  bulbs that stayed silent. A burst of 25 datagrams is exactly what a consumer
  access point drops, and WiFi bulbs in power-save routinely miss the first
  packet, which left them missing from a capture.
- Capture now detects the brightness scale. Govee documents brightness as
  0-100 but some models report the raw 0-254 register; that was being clamped
  to 100, which flattened every bulb above about 39% to full. The scale is
  detected across the whole capture, because a single reading of 51 could be
  51% or 20% and cannot be told apart on its own.
- Capture writes every bulb's raw reading to kodi.log, and the confirmation
  dialog now summarises what it read -- how many colour, white and off, and
  the brightness spread -- so a wrong-looking capture is visible immediately.

v1.1.0
- New "Capture lights as a new scene..." in the Scenes menu. It snapshots what
  every light is doing right now and saves it as a scene. This is the way to
  get a Govee Tap-to-Run into Kodi: run it in the Govee app, then capture the
  result. The saved copy replays over the LAN, so it needs no Govee account
  credentials and no cloud call.
- Scenes can now carry a different setting per light, not just one uniform
  setting for all of them. Scenes without per-light entries are unchanged, and
  a light with no entry falls back to the scene's own values.
- Added bulk status reads: the whole set of lights is queried in one pass
  instead of one bind and one timeout each. Capturing 25 bulbs now costs about
  one timeout rather than the better part of a minute.
- Cloud and LAN state readings are now normalised onto the same keys. The
  cloud reported powerState where the LAN reported onOff, which pushed the
  difference onto every caller.

v1.0.2
- LAN search now sends the scan from every local interface rather than only
  whichever one the routing table prefers, which is what broke discovery on
  multi-homed boxes (VPN, Hyper-V or docker bridge, wired plus wireless).
- Added a plain broadcast fallback alongside the multicast scan, for networks
  that drop or fail to flood 239.255.255.250.
- New "Diagnose LAN search..." tool in the control panel, also reachable as
  RunScript(script.paragon.govee,action=diagnose). It distinguishes the reply
  port being held by another program, the scan failing to send, replies that
  are not Govee, and total silence, and writes the full detail to kodi.log.
- A failed bind on UDP 4002 now names the likely culprit instead of reporting
  a generic error.
- Fixed the diagnostic device count including one entry per probe path, which
  would have reported several times the real number of lights.

v1.0.1
- Fixed the background service crashing on startup with "TypeError: an
  integer is required". Kodi parses xbmc.Player constructor arguments in the
  base type, before a subclass __init__ runs, so the player subclass must
  take no arguments; the service now attaches itself after construction.
- Player callbacks are inert before the service attaches and after it
  detaches, so a callback arriving during startup or shutdown is a no-op.
- Test stubs now reproduce Kodi's constructor-argument parsing for both
  xbmc.Player and xbmc.Monitor, so this class of failure is caught off-device.

v1.0.0
- First release.
- Govee LAN transport: multicast discovery, power, brightness, colour, colour
  temperature and status, with no API key and no rate limit.
- Govee Cloud transport as a fallback for lights without LAN Control.
- Automatic per-device transport selection; LAN preferred when available.
- Devices found on both transports are merged into one entry.
- Control panel: per-light and all-lights power, brightness, colour and colour
  temperature, plus device rename, enable/disable and identify.
- User-editable scenes, seeded with Movie Night, Paused, Lights Up,
  Warm Evening, Paragon Purple and All Off.
- Playback lighting service: applies scenes on play, pause and stop, with
  content-type, fullscreen and delay filters. Only restores on stop if it was
  the thing that dimmed the lights.
- RunScript() actions for keymaps and favourites, with optional per-light
  targeting by name or device id.
